# «Мой ритм» — фронтенд

**Живой сайт:** https://npopko55-cmd.github.io/moy-ritm/

Три экрана из макета: лендинг, обратный отсчёт и плеер тренировки.
React 18 + TypeScript + Vite, без UI-библиотек. Вся палитра и размеры —
в одном файле `src/styles/tokens.css`.

## Запуск

```bash
npm install
npm run dev
```

Откроется `http://localhost:3000`. Если порт занят, задайте свой:
`PORT=3100 npm run dev`.

Сборка: `npm run build`, результат в `dist/`.

## Адрес бэкенда

Один параметр, `VITE_API_URL`. Скопируйте `.env.example` в `.env.local`
(он в `.gitignore`) и поправьте:

```bash
cp .env.example .env.local     # VITE_API_URL=http://localhost:8000/api/v1
```

Переменные читаются при старте dev-сервера — после правки перезапустите его.

Сборка с настоящим API:

```bash
VITE_API_URL=https://api.ritmritm.ru/api/v1 GITHUB_PAGES=true npm run build
```

**Без `VITE_API_URL` включается демо-режим** (`src/api/demo.ts`): регистрация,
вход, тарифы, «оплата» и статистика живут в `localStorage` этого браузера.
Именно так собирается GitHub Pages — бэкенда там нет, а показывать сайт
нужно. На экране входа об этом написано мелкой строкой.

## Экраны

| Адрес                    | Экран                                                    |
|--------------------------|----------------------------------------------------------|
| `/`                      | Лендинг                                                   |
| `/login`, `/register`    | Вход и регистрация; `?next=` возвращает, откуда увели      |
| `/forgot-password`       | Запрос ссылки на новый пароль                             |
| `/reset-password?token=` | Форма нового пароля по ссылке из письма                   |
| `/confirm-email?token=`  | Подтверждение почты по ссылке из письма                   |
| `/confirm-new-email?token=` | Подтверждение смены почты                              |
| `/tariffs`               | Тарифы и оплата                                           |
| `/payment/success`       | «Проверяем оплату» — сюда возвращает GetCourse             |
| `/start/:streamId`       | Отсчёт 3-2-1, затем сам уводит в плеер                    |
| `/player/:streamId`      | Плеер: персонаж, таймеры, переключение потоков            |
| `/settings`              | Настройки тренировки                                      |

`streamId` — один из `cardio`, `back`, `office`, `dance`, `60plus`.

Адреса из писем менять нельзя без бэкенда: их строит он сам от
`PUBLIC_BASE_URL`, список — в `backend/docs/EMAILS.md`.

## Слой API

```
src/api/
├── types.ts    формы ответов, ровно по backend/docs/API.md, и класс ApiError
├── client.ts   интерфейс Api со всеми пользовательскими ручками
├── http.ts     реализация поверх fetch: токен в памяти, refresh по cookie
└── demo.ts     та же реализация без бэкенда, на localStorage
src/auth/
├── SessionProvider.tsx  кто вошёл и что ему доступно; хук useSession()
└── guards.tsx           RequireAuth и RequireAccess
```

Как это работает:

- access-токен живёт **в памяти модуля**, не в `localStorage`; refresh-токен —
  в httpOnly-cookie, поэтому все запросы идут с `credentials: 'include'`;
- при открытии страницы `SessionProvider` молча дёргает `POST /auth/refresh`:
  получилось — человек вошёл, 401 — показываем «Войти»;
- на 401 в любом запросе клиент один раз обновляет токен и повторяет запрос.
  Обновление общее на всё приложение: два параллельных `refresh` с одной
  cookie дадут 401 на втором;
- ошибки обеих реализаций приходят одним классом `ApiError` с полями
  `status`, `code`, `retry_after`, `details`. Опираться нужно на `code`:
  тексты бэкенда будут меняться.

Состояние доступа приходит вместе с профилем (`me.access`), отдельного запроса
«а оплачено ли» нет. Пускать или нет решает бэкенд: контентные ручки отвечают
`403 access_required`. `RequireAuth` и `RequireAccess` только выбирают, какой
экран показать.

## Ролики с движениями

В `public/loops/` лежат 14 зацикленных роликов: `<id>.mp4`, H.264, 640×640,
без звука, около 1.6 МБ на все вместе.

Фон у роликов **не вырезается**. Пробовали: на светлом фоне сайта было видно
обводку по контуру фигуры. Вместо этого ролик целиком показывается в круглой
рамке, и его собственный фон становится частью картинки. Так же сделан круг
на лендинге.

### Как пересобрать ролики из исходников

```bash
bash scripts/build-loops.sh "/путь/к/ЛУПЫ ГОТОВЫЕ/Один цикл"
```

Скрипт масштабирует исходники до 640×640 и кодирует H.264 с CRF 24.
Нужен ffmpeg (`brew install ffmpeg`).

## Музыка

В `public/music/` лежат 13 треков: `<id>.m4a`, AAC 64 кбит/с. Исходные mp3
весили 41 МБ, после сжатия около 17 МБ. Грузится всегда только текущий трек,
это примерно 1–2 МБ.

Проигрыватель живёт в `src/music/MusicProvider.tsx` — один на всё приложение,
выше маршрутов. Музыка включается уже на обратном отсчёте, сразу после
«Влиться в поток», и при переходе в плеер не прерывается. Пауза тренировки
останавливает и её.

Плейлист перемешивается на каждый заход. Трек переключается сам по окончании,
а карточка трека в правой колонке кликабельна — это переход к следующему.
Если браузер заблокировал автозапуск со звуком, карточка подсказывает нажать.

```bash
bash scripts/build-music.sh "/путь/к/Архив 2"
```

Список треков с названиями и длительностями — `src/data/music.ts`.

### Добавить новое движение

1. Положите исходный mp4 в папку с лупами.
2. Добавьте строку в `slug_for()` в `scripts/build-loops.sh`.
3. Перезапустите скрипт.
4. Впишите ролик в `LOOPS` в `src/data/loops.ts` (id, название, длительность цикла).
5. Добавьте id в нужные потоки в `src/data/streams.ts`.

### Добавить трек

1. Положите mp3 в папку с музыкой и допишите его в `slug_for()` в
   `scripts/build-music.sh`.
2. Перезапустите скрипт.
3. Добавьте запись в `TRACKS` в `src/data/music.ts`.

## Картинки, которые нужно подложить

| Путь                        | Что это                                             |
|-----------------------------|-----------------------------------------------------|
| `public/streams/<id>.jpg`   | Фото человека на карточке потока в левом сайдбаре   |
| `public/hero/hero.webp`     | Фигура на главной, вырезана по контуру              |

Требования к фото потоков — в `public/streams/README.md`.

Фигура на главной вырезана по контуру и лежит прозрачным WebP. На ровной
студийной подложке край получается чистым, поэтому здесь вырезка уместна —
в отличие от роликов с движениями, снятых на бежевом фоне, где обводка была
заметна и от вырезки отказались.

Заменить снимок:

```bash
bash scripts/cut-photo.sh /путь/к/новому-фото.png
```

Скрипт сам снимет фон, обрежет по фигуре и пережмёт (562 КБ PNG -> 70 КБ WebP).
Нужны ffmpeg и cwebp: `brew install ffmpeg webp`.

## Что сейчас на моковых данных

Учётная запись, тарифы, оплата и доступ уже ходят в API. На локальных данных
остались:

- **`src/data/streams.ts`** и **`src/data/loops.ts`** — потоки и ролики; id
  совпадают с `app/seed.py` бэкенда. Видео и музыка лежат в `public/`, а не
  раздаются сервером.
- **Правая колонка плеера** — время в движении, «сегодня» и недельный график
  (массив `WEEK` в `src/screens/Player.tsx`). Под API это `GET /stats/summary`
  и `POST /activity/chunks`, инструкция — в `backend/docs/STATS.md`.
- **Настройки** — интервал смены упражнения хранится в `localStorage`
  (`src/lib/settings.ts`). На сервере он уже есть: `PATCH /me/settings`.

Методы для всего этого в клиенте есть (`sendChunks`, `statsSummary`,
`statsProgress`, `getSettings`, `patchSettings`, `supportRequest`) и работают
в обоих режимах — остаётся написать экраны.

## Деплой

Сайт публикуется на GitHub Pages автоматически: любой push в `main` запускает
`.github/workflows/deploy.yml`, который собирает проект и выкладывает `dist/`.

Две особенности подпапки `/moy-ritm/`, о которых стоит помнить при правках:

- пути к файлам из `public/` идут через `asset()` из `src/lib/asset.ts`,
  абсолютный `/loops/x.webm` на Pages ведёт в никуда;
- прямые ссылки вида `/player/cardio` работают за счёт копии `index.html`
  под именем `404.html` — её создаёт шаг в workflow.

Сменить адрес: поправить `base` в `vite.config.ts` под новое имя репозитория.
